## Outcome and boundary

From a project directory, `waywr` identifies or initializes that project, connects to the configured Herdr server, creates or reconnects to one owned project workspace, and opens a responsive Rust/Ratatui interface there. The user can converse with a configured model-backed coordinator, submit one supported drafting/review task, queue more such tasks, inspect workers and artifacts, answer multiple substantive questions, steer or cancel a task, and detach/reconnect while the application continues. One workflow executes at a time **per project**; separate project supervisors may execute concurrently. The existing `wayward-wrangler` and `awp` command names remain compatible, including explicit `--project` diagnostics. A Fish `type -a waywr` check found no local executable/function collision on this host; installation must recheck PATH and refuse an unrelated executable instead of overwriting it.

The first coordinator capability is deliberately narrow: turn a user's message into either a clarification or a **proposed task/steering action** for the existing bounded draft → critique → revision workflow. Structured output may name an action, target task, brief text, explicit context references, and a concise explanation. It cannot call tools, edit repository files, answer human questions, approve artifacts, choose an unconfigured provider/model, change budgets, or dispatch itself. The application validates the action against a versioned schema, project identity, permissions, queue state and frozen run settings; the TUI shows the exact proposed scope and execution cost before the user submits a native task. Status, navigation, answer recording and approval use deterministic application commands. A saved intake clarification may request one bounded coordinator continuation as described below; recording the answer itself consumes no model budget. Coordinator requests arise only from explicit user messages or that recorded continuation; it has its own frozen model/effort and call budget, separate from worker-stage limits. Initial adapters can reuse the installed Claude/Codex structured, text-only CLI process and receipt primitives after adding a coordinator output contract. The operator selects one configured coordinator provider at startup; live provider switching is deferred, while durable application records remain provider-neutral.

## Context boundary and explicit collaboration

Default context assembly uses the current project's task-selected records only. No registry data, neighboring project documents, foreign conversation or foreign native session is supplied. New packet contracts include the project key and allowlisted task data; separate controller execution metadata from the model-visible projection. `artifacts.packet()`/`adapters.real.prompt()` currently serialize the full worker packet, including execution configuration: add an explicit model projection for new contracts and hash/record it alongside the frozen execution packet. Historical prompt/output bytes remain unchanged.

The application resolves allowed document paths under the chosen project, rejects symlink escape and entry into another nested project's marked root, and rejects foreign record IDs unless authorized below. Checking ancestors of an explicitly selected path is boundary validation, not discovering related projects. No unrestricted filesystem/search/registry/Herdr tool is offered to the coordinator or workers. Use fresh native calls, explicit packets, disabled auto-instructions/memory/session reuse/hooks/plugins/MCP and enforced provider tool restrictions. Model proposals may request a relationship but cannot grant it or cause a foreign read.

Current adapters are **not proof of complete native context isolation**: Claude uses an empty tool list/strict empty MCP; Codex disables many tools, but its read-only sandbox can allow reads and the adapter notes a residual `apply_patch` surface. Rejecting a tool event after execution cannot undo disclosure. Before separately authorized native acceptance, preflight must establish that the actual supported interface denies every general read/search/exec tool and automatic foreign context source; otherwise report an adapter-isolation blocker and do not launch. Fake tests prove application packet/dispatch boundaries only. Same-UID trusted native binaries retain authentication/config access; this is application-enforced model context/tool isolation, not OS protection against malicious binaries, same-user processes, manually pasted foreign data, or provider-side account retention. Strong OS containment is a separate scope if required; never claim it from cwd or a prompt prohibition.

**Narrow read-only relationship contract:** an explicit operator request such as “include project B” or an operator-configured relationship is required. Resolve B by explicit path/key (ask only if the name is ambiguous). Record a versioned grant in A's append-only context-access ledger with grant ID/revision, source B key, recipient A key, purpose, task or reusable scope, permitted record kinds and finite path/run/record selectors, byte limit and active/revoked state. Direction is **B → A**, never implied reverse access. An optional versionable relationship config may propose these fields; intentional operator configuration is recorded with its digest as the authorization source. Changed config cannot silently widen a previously frozen grant. Provide typed operator-only `grant_context_access` / `revoke_context_access` commands and `context.access.list` / `context.preview` queries. This is not a model tool or general project browser.

Once the scope is recorded, covered reads need no further confirmation. Select explicit task-relevant artifact versions, decision/finding IDs or document sections within it, at most 16 KiB foreign text inside the existing 48 KiB total context budget; show oversized/ambiguous selection for narrowing, never silently fetch a whole history. If the current task and request already establish purpose/material scope, record them without another confirmation. Otherwise ask only for the missing boundary before reading content; once selectors are clear, resolve automatically. Backend access uses an explicit immutable source binding and a read-only source SQLite connection or its bound compatible reader. Do not call `records.connect()` against B (it creates tables/commits), start B's service, initialize B or acquire B's execution ownership. Incompatible/unavailable explicitly requested sources block that import only. Registry lookup locates B after authorization; no scan or summary of unrelated projects.

Each imported entry records grant/revision, source project key, kind/record ID, source version/hash, selected excerpt and full-source digest, approval provenance where applicable, dependency mode and import time. Store a bounded immutable snapshot in A with these links; snapshots are evidence, not a second mutable source of truth. B's accepted decision is labelled **B's decision**, never silently adopted as A's decision or execution authorization. Do not feed a foreign response through `context.inherited()` as an A human answer; keep imported policy evidence separate from A's canonical decision list. A's own approved task scope/answer determines whether to apply that policy. B retains its own approvals/budgets/tasks. Changes or actions in B require separate authorization and are outside this read-only feature.

Do not traverse B's relationships, links or native sessions. Reject records with known imported/derived foreign context unless independently authorized for A; for this narrow milestone, select B-local records instead of implementing transitive re-export. Carry grant lineage through A's derived artifacts so a later packet cannot bypass revocation by reusing a local copy. Manually embedded undeclared third-party text cannot be detected reliably; the guarantee covers application-recorded provenance, not semantic classification of arbitrary prose.

**Dependencies and revocation:** default imports pin the exact selected snapshot; later B tasks, unrelated decisions and new artifact versions do not invalidate it or trigger refresh. A grant's selectors do not automatically become task dependencies. An explicitly requested `must_match_source` mode verifies only selected record/file hashes before each new dependent dispatch; changed/unavailable selected content stops that task for context review, with original packets preserved. Do not hash B's entire database, final-review object, conversation or all findings: `context.resolve()` currently hashes a whole final object for selected findings, so the new import contract needs object-level digests and explicit source-supersession references. Rebinding B's location does not change content identity. Snapshot revalidation never adds material or changes scope implicitly.

Revocation is appended in A and immediately denies future source reads, exports, and agent dispatch containing that grant's snapshot or derived content, including cached copies; history remains inspectable for operator audit. Serialize grant revision validation with packet publication/execution permit in A. A dispatch already permitted may have received the data and cannot be retracted; revoke stops later access/dispatch, does not pretend to erase native context or cancel B. Other A tasks without that dependency continue. If the task needs that material again, present the narrowly scoped authorization/context decision. Unknown or conflicting source changes are not silently resolved.

## Responsibility and lifecycle

- **Rust executable / TUI:** owns argument parsing, presentation, terminal input/output and the short-lived foreground Herdr client. It invokes the release-paired Python bootstrap helper for project setup/service start; it never creates service units, calls Herdr topology APIs, writes workflow databases, or launches model/worker processes. `waywr ui` is the supervisor-launched pane mode; normal bare `waywr` is the launcher. Closing this client detaches from durable work. Ratatui renders application state; Crossterm supplies terminal events. Use one compatible Crossterm version throughout (initial proof: Ratatui 0.30.2 / Crossterm 0.29, lock exact dependencies/toolchain during implementation). Ratatui provides a test backend, but the application must implement event handling and lifecycle ([backends](https://ratatui.rs/concepts/backends/), [event handling](https://ratatui.rs/concepts/event-handling/)).
- **Python bootstrap helper:** owns project/config resolution, first-setup authorization, location registration and creating/starting the project systemd unit under a setup lock. Returns a versioned JSON launch descriptor; no long-running recovery loop here. It shares the supervisor's unit/descriptor routines so there are no two service-management implementations.
- **Coordinator:** one configured provider adapter converts explicit user messages into versioned proposed actions or clarifications. It receives a bounded provenance-linked snapshot of selected task history, approved decisions, open findings and active operation status. Its native session is optional; a fresh provider call must work from application state alone. Structured output is untrusted until validated. Coordinator calls have durable identity, permission restrictions, transcript/receipt and an independent budget; failure or uncertain execution does not invite silent retry. Its output is shown in the TUI, and its actual CLI execution remains identifiable in Herdr.
- **Python supervisor:** a project-level, single-owner `systemd --user` service with local same-UID IPC and a durable command inbox. Command IDs make reconnect/replay idempotent; the supervisor serializes validation, queue promotion, execution permits, LangGraph transitions, answer consumption and notices. It persists a request before acknowledging it. Model calls are never launched merely because the TUI redraws. An old generation cannot dispatch after replacement. Existing per-run units remain historical; new sessions use the project unit. A runtime check must confirm systemd user-service availability before automatic setup.
- **Herdr:** terminal/workspace/pane display and process hosting through its supported socket API. The app verifies server identity on reconnect and never spoofs Herdr environment variables or scrapes terminal text for authoritative results. Runner receipts, not pane output, prove completion. A changed server identity with unresolved execution preserves uncertainty; a fresh session with no execution may establish its first verified binding; no duplicate pane or call is created on a timeout.

The Python supervisor exclusively owns Herdr workspace/pane creation, focus, UI claim validation and replacement, worker routing, durable state and recovery. Rust registers its UI process through IPC; the service records the claim using peer credentials and verified Herdr identity. Rust may write only its bounded UI cache/outbox, never authoritative application records. A replacement TUI or backend can implement the same language-neutral protocol.

The reviewed startup, detach, stop, recovery and maintenance contracts below govern the new project service. Current per-run controllers and historical records keep their existing behavior.

Steering is an append-only task command. A queued task may receive a new brief/config version before authorization. For an active task, cancellation targets its verified operation; scope-changing steering waits for a stage boundary and shows whether a new task/authorization is required. It cannot edit a frozen packet, silently change worker models or erase accepted answers. Manual input to a worker pane is observable terminal activity, not a recorded decision.

### 1. Startup and Herdr attachment

Resolve `cwd` exactly (no upward repository search); `--project`, `--state-dir` and `--registry-dir` remain explicit overrides. Before starting Python, the Rust entry resolves the selected project's release descriptor using the stable routing contract below and re-execs its bound Rust binary if needed. It then passes the requested paths as argv to that release's paired absolute `venv/bin/python -I -m agent_workflow.session_bootstrap`. Python resolves the project/config, and returns one bounded JSON response on stdout; diagnostics go to stderr. Missing project config returns `setup_required` with the exact files/unit/endpoint to create. The launcher presents one setup confirmation; its accepted request is idempotent. Store an explicit absolute Herdr socket, offering the supported default/inherited value at setup. Never invent `HERDR_ENV` or target a focused pane by omission.

Bootstrap JSON v1 returns `project_key`, resolved project/state paths, service IPC path, unit identity, absolute Herdr executable/socket, release/protocol IDs and service readiness. Bootstrap/setup failure returns a structured error and exits without entering raw mode. After starting the unit, its IPC must become available **before** Herdr readiness: otherwise cold startup would deadlock. Python service startup and unit recovery use the lifecycle rules below; Rust does not call systemctl or manage supervisor restart counters.

Outside Herdr, Rust starts normal `herdr` with inherited terminal stdio and the configured `HERDR_SOCKET_PATH`. [Herdr autodetect](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/server/autodetect.rs) starts a server when absent; [socket rules](https://github.com/herdrdev/herdr/blob/7b116c05bfda646af39d2524c54e70c751f57ee8/src/server/socket_paths.rs) pair API and client endpoints. Rust never enables raw mode in this outer launcher. The supervisor handles an idempotent `ui.attach` request, waits for peer-validated Herdr readiness, then creates/focuses an owned workspace and launches the **absolute release-pinned Rust executable** in `ui` mode. Record intent/token before each mutation; reconcile lost responses by verified identity, otherwise stop uncertain. A UI pane claims its token via IPC; the service verifies UID/PID/start/boot and the Herdr token/argv/pane binding before acknowledging readiness.

The launcher monitors client exit and service readiness for at most 30 seconds. On failure it records diagnostics through the backend when reachable and closes only its own foreground client (bounded TERM, then KILL of that verified child if needed). Never signal Herdr server or descendants. If the service is unavailable, show unit/socket diagnostics directly; no infinite spinner. Inside an actual managed pane, request the same `ui.attach` and return without launching a nested Herdr client. An identical attachment request cannot create a second pane. A cleanly detached/dead UI can be replaced only once absence is verified; a live UI without matching pane remains uncertain. Closing a TUI does not stop a task or require a replacement UI to keep execution alive.

Compatibility routing belongs to the Rust CLI parser: no subcommand launches the UI, `session ...` addresses the service, and existing command grammar delegates unchanged argv/stdio/exit status to the paired `agent_workflow.cli`. Do not scan arbitrary argument values for command names. Python routes mutations for session-owned tasks through the service command facade; direct legacy graph mutation is refused while a project service owns the store. Explicit historical runs keep the old path with existing locks/fences when no competing owner exists. `wayward-wrangler` and `awp` are aliases of this dispatcher, with legacy `--project` semantics intact.

Rust ordinary-terminal cold/warm startup, inside-Herdr reconnect, lost creation reply, closed UI replacement and duplicate launcher are mandatory early runtime gates. Prior Python startup does not discharge them.

### 2. Nonblocking supervisor and bounded concurrency

The service owns a Unix socket under `$XDG_RUNTIME_DIR/waywr/<full-project-key>.sock` (0700 parent, 0600 socket, peer UID check), a lifetime `supervisor.lock`, and a monotonic generation. It keeps SQLite transactions short. Its main loop handles IPC, commands, event cursors, status, cancellation and receipt polling. It must never call `graph.invoke`, blocking Herdr requests, CLI authentication, or a model process wait on that loop: use bounded I/O jobs and one dedicated graph-driver thread with its own SQLite connection and explicitly bound project/runtime paths and generation context. `runtime.py` and `ownership.py` use ContextVars; bind both in every background job/thread rather than assuming thread inheritance or falling back to checkout-local state. UI polling/subscription uses persisted application events; Herdr events only invalidate presentation caches.

The driver serializes LangGraph mutations under the existing controller lock. Before every stage dispatch it checks the owner generation, task authorization, pause/cancel/steering requests and remaining budget under a short dispatch fence. Waiting on an existing receipt may block this thread, but cannot block the control loop. Control commands are durably accepted without taking the graph lock; no SQLite transaction or dispatch fence may be held across an external wait; answers are consumed by the driver at its gate and steering at the next stage boundary. Cancellation records task intent immediately; if a claim exists it writes the claim-bound cancellation request. A cancellation received before permit prevents permit publication. If completion wins the race, its validated receipt wins and the user sees “already completed,” not a fabricated cancellation.

Within each project there is one executing workflow and at most one coordinator call at a time. A coordinator call may overlap a worker so conversational input remains useful, but it never creates a second executing workflow in that project. Additional user messages can queue. Both operation kinds use separately identifiable Herdr runner panes and immutable execution evidence. Coordinator operations live under `session/coordinator/<operation-id>/`, with a distinct budget reservation; workflow operation paths/limits remain unchanged. No general scheduler or new backend is needed. A coordinator failure stops that conversation action, not the unrelated active workflow. A service crash kills its driver thread but leaves Herdr workers; restart verifies the old service is dead, increments generation and reconciles original operations before resuming. Missing reports or timeouts never authorize another attempt.

### 3. Durable command and proposal contract

Use additive session/task/command/event tables in the selected state database, separate from legacy run tables. Required fields:

- `task`: application ID, queue sequence, `task_version` (brief/scope/context/settings), `state_revision` (each authoritative task transition), status, bound run ID, authorization digest, desired pause/cancel state.
- `command`: UUID, project key, action enum, target task, expected task version/state revision where applicable, canonical payload digest, actor kind (`human` or `coordinator-proposal`), accepted/rejected/applied outcome and resulting event sequence. Same UUID+digest returns the original outcome; same UUID with different content is a conflict. Commit before acknowledging; acceptance is not a claim that an external action completed.
- `coordinator proposal`: call/response hashes, application proposal ID, one action (`propose_task`, `propose_steering`, `request_clarification`, or `reply`), referenced task versions, decision revision, context digest and candidate hash. Validate both at result ingestion and at application. A stale proposal is preserved and labelled stale; no automatic regeneration/model call. A read-only historical reply can still be displayed as such. Unrelated task updates do not invalidate a proposal; changes to referenced state do.

The command enum is limited to `submit_message`, `admit_task`, `apply_steering`, `answer_question`, `approve_candidate`, `reject_candidate`, `cancel_task`, `pause_queue`, `continue_queue`, `stop_session`, `grant_context_access` and `revoke_context_access`; diagnostics/navigation are read-only. Cancellation targets the application task plus exact current operation identity; receipt reconciliation handles a concurrently completed target. No raw shell command or arbitrary method name is accepted.

**Queue skipping resolution:** do not add a `skip_task` command. Remove the former step-3 “skip” shorthand. The operator may explicitly `cancel_task` on a queued/unlaunched task or abandon a safely stopped task; that command records cancellation without deleting artifacts or decisions. For a stopped task, first verify no live child, unresolved launch/receipt, pending uncertain execution or surviving ownership. Missing evidence refuses abandonment. A running task needs targeted cancellation and a resolved terminal outcome before the queue advances. Coordinator proposals cannot authorize this action. No silent skipping, budget reset, or revival of a cancelled task; continuing its work needs a new task authorization.

Only the deterministic application may convert a human-approved proposal into a task authorization. Coordinator prose or structured output cannot set the actor to human. Direct question answers bind request ID, request digest, decision revision and context; final approval also binds the displayed artifact hash. Persist conversation and command IDs before sending calls, so reconnect does not repeat messages. The TUI restores events from its last sequence; events and task projections update in one transaction. No transcript becomes a substitute for canonical decisions.

### 4. Service, stop and maintenance contract

New unit name: `wayward-wrangler-project-<full-project-key>.service`. First setup creates only this application-owned unit and descriptor; start it on demand, **do not enable it at login or enable user lingering** in this milestone. Use `Restart=on-failure`, two-second restart delay and at most four starts per 60 seconds. Persist infrastructure recovery attempts per cause/operation (three attempts with 1/2/4-second delays); restarts must not reset that budget. Task-level failure leaves the service responsive. A fatal service failure beyond systemd's limit is shown by the launcher with durable diagnostics; it does not reset failure counters automatically.

TUI close/quit means detach: queued authorized work continues. `waywr session stop` means persist scheduler pause, prevent new permits, cooperatively detach the driver and exit the project service; existing Herdr workers may finish and retain receipts, but no next stage starts. It does not close worker panes or stop Herdr. Offer cancellation as a separate explicit task action. The next `waywr` opens the paused session for inspection; one “Continue queue” action resumes existing authorization. A normal detach/reconnect needs no such action. Completion keeps the project service idle and available. Persistence survives user logout/reboot; uninterrupted execution across logout is not promised without separately configured user-service/Herdr lifetime.

Upgrade a selected project only when that project has no nonterminal run/coordinator execution and its service is stopped; keep the paired release and interpreter environment available. A new client and old service exchange release/protocol/state versions before commands; mismatch exposes only version/diagnostic information. A forced component replacement must trigger version refusal, not rewrite the envelope or restart a worker. Use the side-by-side installation and rollback rules below; no hot code reload or automatic downgrade. Relocation likewise checks only that project: stopped service, no active/uncertain operation and explicit location rebind; append a new service/location binding, verify evidence hashes and update the index/unit without rewriting history. Queued plans whose path/config digest changes require reauthorization. Unsupported whitespace/unit escaping must be handled with tested systemd argument escaping or explicitly refused before writing a unit; do not copy the current naive join into new setup.

### 5. Authorization and question behavior

The operator approves project setup once, coordinator settings and its bounded session budget, and each new task's concrete frozen plan once. Typing a coordinator message authorizes one call within that budget; status, answers, review and deterministic cancellation use none. Queue promotion, ordinary stage transitions, answer consumption, verified receipt reuse and bounded infrastructure recovery continue under the recorded task authorization without repeat confirmation. Changes to scope, inputs, models, effort, budget or selected context produce a new task version and invalidate its old admission; they cannot mutate a running packet. Scope-changing active-task steering pauses before the next dispatch and proposes a follow-up plan. Pure navigation/status commands never require a model.

Version the new workflow/question contract for new runs only. Preserve the current four-question output-size bound but remove the one-question-per-run gate; a task may accumulate further questions over its bounded calls. Serial presentation gives each question its own stable ID, origin and immutable answer. Questions about already accepted topics require new evidence and explicit reconsideration. An answer does not consume a model call or grant a new slot. No remaining author slot means an explicit blocked follow-up, with the answer preserved and no misleading approval of an artifact predating it. Intake clarifications use a separate application request kind bound to task/proposal version and context, since no candidate artifact exists yet; they must not call `prepare_choice` with a fabricated artifact. If clarification requires another coordinator interpretation, the request records `continuation=coordinator` and reserves no call until all answers are saved; the supervisor may then make one call under the remaining coordinator authorization. If the budget is exhausted, retain answers and show a blocked action. Worker questions continue through LangGraph after completed-stage publication. Do not carry the old product-spec prompt's instruction to raise the editing-policy question into a follow-up that already inherits that decision.

## Local protocol v1 — language-independent contract

Everything in this section is proposed; no cross-language IPC or Rust runtime has been implemented or tested.

Commit `protocol/session-v1.schema.json`, JSON request/response fixtures, and `docs/session-protocol.md` during implementation. They define wire types, status meanings and preconditions independently of Python classes, LangGraph checkpoints or Rust structs. JSON objects/arrays, UTF-8 strings, booleans and bounded integer counters only; IDs and SHA-256 values are strings. No pickle, Python exception objects or arbitrary callable names. Rust serde types and Python validation consume the same fixtures; JSON Schema is the contract, not an autogenerated Python model.

**Transport/framing:** Unix stream socket at the project endpoint above, same-UID `SO_PEERCRED` verification in both directions. UTF-8 newline-delimited JSON; embedded newlines must be escaped, duplicate keys/nonfinite numbers refused. Read incrementally with a 1 MiB frame ceiling before allocation; invalid/oversized frames close that connection. At most eight connections per project service. One Rust connection handles commands/queries, another reads event batches, so slow event delivery cannot prevent cancellation. Backend request handlers never wait for a graph lock or model completion. Invalid frames have no action; accepted action errors remain durable.

| Message/API | Required contract |
|---|---|
| `hello` / `hello_result` | First frame on each connection: protocol major/minor, release ID, project key, client ID, requested channel. Response adds owner generation, state schema and capabilities. Major, exact release or project mismatch refuses mutations; diagnostics only. Minor changes may add optional fields, never reinterpret a command. |
| `command` | Request UUID plus stable `command_id`, action enum above, target, expected task version/state revision and relevant decision/context/candidate bindings, typed payload. Service derives provenance; incoming coordinator data cannot label itself human. Commands ≤64 KiB; composer text ≤32 KiB UTF-8. |
| `command_result` / `command.get` | Echo IDs, `accepted`/`rejected`/`applied`, outcome/event sequence and current references. Same command ID+payload returns stored outcome, even after restart; changed payload is `idempotency_conflict`. “Accepted” means durably queued, not completed. `command.get` resolves a lost reply. |
| `snapshot`, `tasks.list`, `task.get`, `history.read`, `artifact.read` | Read-only bounded projections, not graph internals. Snapshot gives a cursor watermark in the same read transaction; paged historical data uses stable IDs/before-cursors. Artifact chunks ≤64 KiB, bound to artifact ID+hash; any hash change refuses review/approval. Larger bodies are paged, never truncated silently. |
| `events.read` | `after_seq`, limit ≤64, wait ≤1000 ms. Reply ≤256 KiB with ordered durable events and `next_seq`; no unbounded push stream. Event has schema version, sequence, type, project/task IDs, versions, timestamp and bounded body or artifact reference. Types: task/operation state changed, question opened/answered, artifact published, proposal ready/stale, notice, session state changed. |
| `ui.attach`, `ui.register`, `ui.detach`, `worker.observe`, `artifact.open` | Explicit display-only requests to Python's Herdr integration, with project/operation/artifact/UI-token identity. Attach is idempotent. No arbitrary argv/socket methods. `artifact.open` reuses verified read-only Vim routing; observation/manual pane input never records a decision. |
| `error` | Stable code, message, request/command ID if known, current versions, safe operator action and `execution_state` (`not_dispatched`, `in_progress`, `completed`, `failed`, `uncertain`, or `not_applicable`). Codes include invalid_request, protocol_mismatch, stale_state, idempotency_conflict, unauthorized, busy, not_found, resync_required, uncertain and internal_error. No “retryable” flag that could authorize another model attempt. |

A timeout is a transport outcome. Reconnect/query or resend **the same command ID and exact payload**; never make a new dispatch command to obtain a reply. Before sending, Rust stores a bounded 0600 outbox under the user-local client cache keyed by project/client ID (128 pending commands maximum). Remove an outbox entry only after backend acknowledgement; it is delivery bookkeeping, not workflow authority. Full outbox disables submission with a visible message. Service actor provenance separates operator UI actions, explicitly authorized automation and coordinator proposals; same-UID IPC is a local trust boundary, not cryptographic proof of a human click.

All IPC queries, command IDs, cursors, outboxes and grant records are scoped to the endpoint's project key. Reject a payload naming another target project; only the explicit read-only import resolver can dereference an authorized source project. There is no `projects.list` or foreign-task endpoint available to the coordinator. `context.access.list` is operator inspection and is not copied into model snapshots.

Task status values are `queued`, `active`, `awaiting-input`, `blocked`, `recovering`, `failed`, `uncertain`, `output-invalid`, `cancelled`, `approved`, and `rejected`. Operation execution state is separate from artifact quality: a structurally usable incomplete revision is provisional with carried findings, not uncertain execution. Unknown outcomes stop mutation and request a compatible snapshot. State revisions advance on authoritative transitions, not activity heartbeats. Plan/artifact digests remain internal bindings supplied by the backend; interactive confirmations show scope/settings or the reviewed candidate without manual hash copying.

Durable events and task projections commit together. Reconnect obtains a snapshot watermark, then reads events after it; duplicate sequences are ignored, gaps/unknown mandatory event types trigger snapshot resync. History remains in backend storage; Rust keeps only a 200-item/2 MiB display window and paginates older content. Each IPC thread has a bounded 16-message channel; at most one event batch is outstanding. Stop requesting batches when full. Do not enqueue terminal transcripts into the durable event stream: coalesce disposable activity indicators per operation at ≤4 Hz, keep stdout in existing transcripts/visible panes, and page transcript previews on demand. Slow UI clients may be disconnected after five seconds of blocked output and resume from their cursor. Critical state/decisions are never discarded with activity indicators.

Rust uses one terminal event/render loop and two blocking IPC worker threads with deadlines and bounded channels; no extra async runtime is required for this scope. Terminal input is serviced every iteration; process at most one event batch before polling input again. Redraw only on changes or a pending effect frame, at most 30 Hz; there is no continuous idle repaint. Python's control loop uses asynchronous socket handlers and bounded I/O jobs plus the single graph-driver thread already specified. Admission, streaming and graph progress must not hold locks needed for input acknowledgement.

## Distribution recommendation — paired local release bundle

Use one **Linux x86_64 glibc release tarball** initially (the inspected host architecture), containing `bin/waywr`, the existing Python application wheel, a complete matching CPython 3.12 dependency wheelhouse, a hash-pinned install requirements file, release manifest and a small Python-stdlib installer. This supersedes pipx as the primary milestone-6 installation route; the wheel remains the backend build artifact. GitHub Releases may host versioned bundles later, but publishing is outside implementation acceptance. No public PyPI, Rust crate publication, OS package or automatic downloader is needed.

Python remains an explicit prerequisite: require a system CPython **3.12 with venv/ensurepip** for this first bundle. The installer checks architecture, glibc compatibility, interpreter version and available wheel tags before changing public commands; refuse clearly if absent. It does not install or update system Python. Herdr, systemd user services and (for separately authorized native use) selected agent CLIs/authentication remain external prerequisites. Ratatui does not remove this dependency. Test and record the minimum build/runtime glibc baseline; no portability claim to untested distributions or architectures.

Install into a new final path under `~/.local/share/wayward-wrangler/releases/<release-id>/` (explicit prefix/bin-dir overrides for tests). Copy the Rust binary/assets, create `venv/` there with the selected interpreter, and install only bundled wheels using `--no-index`, `--only-binary=:all:` and `--require-hashes`; no editable import or source checkout. Validate the paired executable/backend version and resources, then register the installed release. An explicit default-selection action may atomically switch the owned `current` link used by `~/.local/bin/waywr` and aliases; it selects the default for **new/unbound projects only**. Installing or selecting a default never upgrades an existing project or starts its service. Never overwrite an unrelated executable/alias. Supply a Fish-compatible manual command to add that bin directory to PATH only when needed; do not edit shell config automatically. Venvs are created at their final paths because Python documents them as generally nonportable ([venv](https://docs.python.org/3.12/library/venv.html)); bundled wheels and hashes provide controlled offline installs ([pip repeatable installs](https://pip.pypa.io/en/stable/topics/repeatable-installs/)).

**Stable release routing:** `.wayward-wrangler/release.json` is a small version-1 descriptor (project key, bound release ID/manifest digest and binding generation), maintained by Python as a projection of appended project release-binding records. Rust reads only this routing descriptor and the selected installation manifest before opening workflow state. Validate the release ID against the installed catalog; no arbitrary executable path from project data. If the bound release differs from the default entry, re-exec its absolute `bin/waywr` with the original argv/stdio and a loop guard. Handshake/project identity validation then occurs entirely within the matched Rust/Python pair. Route compatibility commands, explicit state overrides and project-qualified review links the same way. Unknown routing version or missing bound release yields an exact install/repair instruction; never silently substitute or migrate. Existing initialized projects without a binding require an explicit compatible binding step; historical legacy access stays explicit, without rewriting saved envelopes.

The selected binary resolves its canonical executable path to its own manifest and `venv/bin/python`, invokes with `-I -m`, and never imports from cwd/PYTHONPATH or searches for another interpreter during normal use. Manifest fields remain paired release IDs, IPC version, supported state schema range, wheel/resource hashes and interpreter requirement. Herdr pane argv, runners and service ExecStart are pinned to that release, not `current`. Shared review-plugin assets are installed explicitly with rollback registration retained; the handler uses the project-qualified location/release router and cannot assume all projects use the plugin's installation release. Existing historical plugin installations remain untouched until a separately approved switch.

**Install/default selection versus project upgrade:** installation and default selection do not open project stores or check their execution. `waywr --project A session upgrade --release R` invokes A's bound maintenance helper, acquires only A's maintenance/admission locks, verifies A's quiescence and target compatibility, then appends an upgrade-intent/binding record and atomically updates A's descriptor/unit. Stop only A's service as part of the explicit operation; start it on the next attach in the recorded paused state. Busy/uncertain A refuses its own upgrade, but B's status or availability is never inspected. A keeps the old binding if validation fails. Interrupted binding/unit updates are reconciled against A's intent before any dispatch; no mixed-generation service may start. Newly added schemas stay additive and versioned.

`session rollback --release R` applies the same checks to the chosen project, and additionally requires that retained R supports its **current** schema. Never restore stale state or translate historical hashes to fit older code. Different projects may stay on different releases indefinitely; default-link changes do not redirect existing service/pane execution. Explicit target release settings are integrity choices, not new worker/model permissions. Project relocation checks only its old/new state locations and appends routing records. Relocating an installation prefix recreates that release's venv and explicitly rebinds affected project/service paths; unrelated project operation continues with retained releases.

**Retention/deletion:** maintain small installation reference records per project for current and retained compatibility releases, created before committing a project binding; crashes may conservatively leave an extra reference. These contain location/release metadata only, no model context. Never delete a referenced release/interpreter environment. Deletion (deferred; no automatic garbage collection in this milestone) must check references and refuse when a missing project prevents establishing that its reference was retired. This conservatism applies only to deletion, never startup, install, default selection or another project's upgrade. Do not run installation-wide quiescence scans.

## Future Rust consolidation boundary

Python retention is a milestone choice. Keep the existing code behind a small command/query facade used by IPC and compatibility CLI; expose task admission, decision recording, workflow advance/reconcile and inspection with explicit inputs/outcomes. Do not introduce generic storage/engine plugin layers or duplicate workflow policy in Rust. LangGraph remains an internal progress implementation; wire snapshots expose documented task/stage/operation/gate states only.

Document `docs/state-contract.md` during implementation: each new persisted record has `schema_version` and semantics, separate from IPC/release versions. Record command ID/digest/outcome, task version and transitions, event ordering, immutable inputs, finding origins/assessments, decision references, exact approval bindings and appended routing/recovery evidence. A table records existing unversioned legacy fields and their frozen legacy interpretation; do not add fields to historical bytes. Unknown required record versions refuse mutation. SQLite schema migrations have an explicit version and transactional additive changes. Events are a notification journal; canonical decision/artifact/receipt records remain authoritative, not a new competing event-sourced database.

Concrete migration difficulties: LangGraph's SQLite checkpoint format and Python serializer are not a portable Rust workflow snapshot; ContextVars/path globals and `cli.py` orchestration coupling need care; native-adapter subprocess streaming/permissions, receipt recovery and Herdr/systemd process identities require equivalent behavior; `storage.canonical` and existing JSON/file hashes must match exact historical bytes (including Unicode and whitespace), not merely equivalent objects. Findings have both legacy and v2 meanings. Python runtime/dependency/resource packaging must remain available until these responsibilities move. Record semantic schemas and byte fixtures now, but implement no new migration/export system in this milestone.

Incremental future path: (1) keep the Rust client and protocol stable while replacing a bounded backend capability behind the facade and running the same black-box scenarios; (2) replace workflow execution for **new runs** after matching policy, permits, cancellation, questions and failure behavior; leave active/historical LangGraph runs with a pinned Python reader/driver; (3) only with separate migration authorization, export verified neutral snapshots at quiescent boundaries and append import/provenance records to a new store, then retire Python when legacy access is covered. Never translate live checkpoint internals or claim exactly-once native execution from a serializer conversion. Running both engines during transition costs packaging and compatibility work; a one-time complete rewrite instead concentrates recovery/integrity risk. Neither is part of milestone 6.

Acceptance must therefore use public CLI/IPC actions, receipts/artifact hashes, observable worker invocation counts and task/gate outcomes. Existing Python unit tests remain useful regression coverage, but replacement compatibility is not defined by internal class layout or patched checkpoint fields.
