## 1. Runtime and SQLite architecture

The approved [proposal](rust-backend-migration-proposal.md) (Storage bullet and dependency table) specifies Tokio for sockets/timers/async pipes and a **dedicated SQLite writer with bounded requests**; full mailboxes should return busy before command acceptance. [Stage 5](rust-migration-log.md) first reports the deviation at commit `7ef2ef1af9177ef8352c718c206b9aaed9299f4a` and says scoped fake tests were responsive. The commit introduces `backend/src/session_service.rs` and `backend/src/session_store.rs`. Neither the commit, migration log, nor retained summaries record an incompatibility, benchmark, measured advantage, or separate approval for the change. The apparent reason is implementation simplicity; that is an inference, not a verified finding.

**Implemented:** One project service process holds `session/service.lock` and a generation in `supervision/owner.json`. Its accept loop spawns one scheduler thread and at most 32 simultaneous per-client threads (`backend/src/session_service.rs:10-17,68-107,533-555`). Above the cap it drops a socket, with no typed busy response. Each client has 10-second read/write timeouts; an event poll can occupy its thread for one second (`session_service.rs:102-137`). The scheduler serially polls coordinator/workflow/drain and sleeps 150 ms; Herdr control is synchronous with socket timeouts (`session_service.rs:556-574`, `backend/src/herdr.rs:17-31`). `dispatch_gate` fences several reservation/stop paths; `attach_gate` serializes UI attachment. Three unexpected scheduler errors append error records and attention events, then stop the scheduler while IPC can remain alive (`session_service.rs:533-555`). Orderly service exit joins the scheduler, but client threads are detached and not explicitly joined (`session_service.rs:83-100`). The Rust TUI has separate command and event threads with 16-frame synchronous channels, reconnect/outbox replay, and a main input/render loop (`frontend/src/main.rs:168-289`). Detaching ends that UI process, not the project service.

Each Herdr-visible runner is a separate process; a child has two pipe reader threads feeding an **unbounded** `mpsc::channel` (`backend/src/runner.rs:152-176,219-260`). The runner writes transcript and terminal output on its consumer thread. The 32 MiB stdout check happens *after* receipt from the unbounded channel; it does not bound queued memory, stderr, or the transcript (`runner.rs:261-305`). Native child execution has a ten-minute deadline; cancellation targets a verified process group, with SIGTERM then a three-second SIGKILL escalation (`runner.rs:270-286`). On return or unresolved execution, the runner keeps its Herdr pane inspectable rather than releasing it as a service thread. These lifetimes are process-owned, not Tokio task-owned.

**SQLite authority:** The same project's scheduler and IPC threads may both open writable `rusqlite` connections; `Store::connection` sets WAL, `synchronous=FULL`, and a ten-second busy timeout (`backend/src/workflow_store.rs:75-125`). `session_store.rs:271-305` takes a deferred snapshot transaction; mutations such as `submit`, `service_attention`, and task transitions use immediate transactions and commit before returning (`session_store.rs:440-475,656-675`). Workflow reservations/results use immediate transactions in `workflow_store.rs`. No dedicated writer or bounded write mailbox exists. SQLite serializes writers, but a caller can block up to ten seconds waiting for its connection/transaction; this is not the proposal's pre-acceptance busy contract. An SQLite error propagates to the calling handler or into the scheduler's three-attempt attention path; there is no writer-thread failure/restart state. Source shows `dispatch_gate` can be held while a database call or Herdr reconciliation occurs (`session_service.rs:575-620,640-662,778-785`); no complete lock-order audit or contention test is recorded. No external I/O inside a SQL transaction was found in the inspected critical paths, but that has not been proven exhaustively.

**Actually tested:** The Stage-5 installed fake fixture checked status in under one second while a three-second fake worker ran, active-work exit and receipt reuse, systemd KILL restart, and cold Herdr attachment (`tests/rust_migration_stage5.py:175-190`; `.local/rust-migration/stage5/{active-exit-01,systemd-04,cold-03}/summary.json`). Stage 6 repeated an installed fake flow with two projects, exit, missing-workspace route, question and approval (`.local/rust-migration/stage6/verified-live/summary.json`). Unit/fault tests cover command replay, scheduler failure notices and execution safety; the Stage-5 differential exercises *no-worker* command/event/lifecycle transitions (`tests/rust_migration_stage5_differential.py:10-70`). No retained test establishes latency with 32 slow clients, a held SQLite writer lock, stalled Herdr I/O, high-rate stdout/stderr, or simultaneous answer/cancel/exit/reconnect. The 32-connection cap bounds thread count, but not output-channel memory or end-to-end response latency.

**Impact and smallest check:** Slow or numerous clients can occupy the whole pool; a contended database can delay status, decisions or cancellation; a chatty CLI can grow runner memory before the stdout limit fires. Before real asynchronous coordinator/worker acceptance, use isolated fake workers and a private Herdr service to hold clients open, hold a separate SQLite write lock, flood both child streams while slowing the consumer, and race answer/cancel/exit/reconnect. Measure bounded memory and control latency; assert one reservation/receipt and durable attention after failure. If the current design cannot meet those bounds, add a bounded output path and serialized/bounded DB writes (and adopt async I/O where blocking threads remain a problem), then repeat those focused checks. Do not claim Tokio alone fixes external-call recovery.

## 2. CLI compatibility inventory

The r9 parser/handlers are `src/agent_workflow/cli.py:399-690`; the r9 Rust shell forwarded run commands to that installed Python module and session maintenance to `session_bootstrap.py` (`git show 7961544:frontend/src/main.rs`, around lines 602-790). The new dispatch is `frontend/src/main.rs:499-630` and `frontend/src/rust_cli.rs:42-132`. For a Rust-bound project, `route_bound_release` verifies its manifest, then Rust handles or refuses the command. It only `exec`s another release when the project is **explicitly bound** to that available, verified release. If unavailable, it errors; there is no silent Python fallback. `legacy-inspect` is a new read-only exception requiring an explicit state path. The installed Stage-6 tests cover fake flow, selected release routing, plugin links and historical inspection, **not this full command/flag inventory** (`docs/rust-migration-log.md`, Stage 6; `tests/rust_migration_stage5_differential.py` is a no-worker store trace).

Classification: **P** preserved sufficiently for the stated contract; **C** changed (rationale/authorization must be reviewed); **L** deliberately restricted to a bound r9 release; **M** missing or regressed on a Rust-bound project. “CLI” below means a callable user/automation command, not a TUI action.

**Global and hidden flags:** r9 parses `--color`, `--project`, `--state-dir`, `--registry-dir`, `--legacy-origin` before subcommands (`cli.py:399-405`). Rust recognizes these names for routing, but `--color` and `--legacy-origin` have no equivalent effect on Rust-bound projects; `--project` and `--state-dir` apply to project/state selection, and `--registry-dir` to location/review operations (`main.rs:494-552`, `rust_cli.rs:11-40`, `rust_review.rs:10-19`). New `--herdr-socket`, `--ipc-dir`, `--release` apply to project service/installation. Most old subcommand flags are not strictly parsed, so refusal or silent ignoring depends on handler. The approved [proposal's CLI gate](rust-backend-migration-proposal.md) explicitly lists diagnostics, decisions/review, maintenance, preflight/start/resume/cancel, probes and integration; it permits explicit refusal of **unsupported legacy mutation**, not wholesale relabeling of ordinary CLI controls as “historical.” The existing Stage-6 tests do not discharge that gate.

Rust adds `legacy-inspect RUN --state-dir DIR` for read-only historical records, plus `bundle-build` and `bundle-install` for paired releases. `--backend-info`, `--protocol-probe`, and `--lost-reply-probe` are implementation/verification entry points, not r9 user commands (`frontend/src/main.rs:605-630`). Their presence does not replace the missing ordinary controls above.

**Recommended targeted follow-up:** A table-driven parser/handler comparison using the frozen r9 executable and copied state, plus isolated Rust fixtures for every accepted/refused form, should first establish intentional contracts. Restore the ordinary commands/flags above through the existing project service and evidence APIs, or obtain an explicit product decision to retire each one with a documented replacement and script migration. Do not route a Rust-bound project to Python or revive a second scheduler. Trial-specific `adopt-*` and foundation probes may remain restricted with clear error text. No command was restored in this review.
